## 2026-09-13 Conversation Persistence V1

### 目的

ChatGPT ProjectでConversationを切り替えても同じ開発作業を安全に復旧できるようにしつつ、誤Resume・古いBackfill・書込み途中の中断・複数Writer・保存成功の誤判定でCurrent Stateを壊さないConversation Persistence V1を実装した。

Conversation / Workstream / Live GuardはRecovery Evidenceとして使い、Current Repository / Requirements / Branch / PR / CommitをProject StateのSource of Truthとして維持する。

### 実装

`EliteMay/web-project-data`:

- `recovery.stateEffect`へ`current / historical / correction`を追加し、Historical Backfill / CorrectionがCurrent Conversation / Workstream Stateを巻き戻さないようにした
- `occurredAt`がtrusted `capturedAt`より5分超未来の場合を拒否し、future timestamp poisoningを防止した
- Workstream lifecycleを今回処理中の1件ではなく保存済みInteraction全体から導出するよう修正し、古いBackfillで`completed`等が誤って戻る経路を閉じた
- Workstream TopicsをCurrent state-bearing Interactionから再導出し、長期Workstreamのstale topic蓄積を抑えた
- Workstream作成へretry-stableな`creationKey`を追加した
- Resume Proposal / Confirmation / Rejection / Failure Reviewをtyped `resumeEvent`として保存可能にし、caller-supplied booleanをConfirmationの正本にしないようにした
- Automatic Resumeは軽量Indexで候補を絞り、Candidate Checkpointをsemantic interpretationへ渡す構造へ分離した
- `live-interaction.schema.json`とLive Guard helper / regression testを追加した
- Live Guardは`workstreamId / conversationId / interactionId / basedOnInteractionId / intentHint / writeBaselines[]`を持ち、Secret sanitize、baseline classification、settlement判定を実装した
- Canonical Persistence Receiptを強化し、Interaction / Conversation Checkpoint / Workstream association / Correction evidenceを再読込確認するようにした
- Correction source WorkstreamではCorrection Interactionを通常`interactionRefs`へ残さず、誤Association除去 + `corrections` evidenceを成功条件として扱うよう修正した
- canonical multi-file persistenceをGit tree / commit / fast-forward-only ref updateで1 logical transactionとして公開できるContractを追加した
- `recovery-live`専用Branchを初期化し、短期coordination stateをCanonical `main` historyから分離した

`EliteMay/web-project-guide`:

- `docs/23-conversation-handoff-recovery.md`をV1 Contractへ整理し、既存Handoff / Current work ref / Failure Review / Parallel Lease Ruleを残したままLive Guardを統合した
- Workstream candidate resolutionをsemantic interpretationとdeterministic hard gateへ分離した
- Automatic Resumeで候補を推定した場合は、現在Conversation内の具体的Proposalに対して1回だけUser Confirmationを要求するContractを維持した
- Workstream Resolution / Confirmation / Write Target / Live Guardを別Gateとして扱い、どれかが未解決ならRepository writeを許可しないようにした
- Userが候補を否定した場合は別候補へ即切替せず、Failure Mechanism / Root Causeを先に確認するRuleを維持した
- Live Guard失敗時のdegraded mode、unsettled Guard recovery、Current Repository再取得、Platform-level hook非保証を明文化した
- Conversation Persistence / Root-Cause Validatorを旧文言の完全一致ではなくCurrent意味Contractを検査する形へ更新した
- `UNRELEASED.md`へV1変更を記録した

### 実装中に検出したFailure

#### 1. Correction Receiptの誤Oracle

Data PR #118の初回CIでは、Correction Interactionがsource Workstreamの`interactionRefs`へ存在しないことをFailure扱いして落ちた。

しかしCorrection sourceでは、古い誤Associationを外すことが正しいため、新しいCorrection Interactionを通常Referenceとして残す必要はない。

修正後は:

```text
Correction source
→ stale corrected InteractionがinteractionRefsから消えている
→ correctionsにCorrection evidenceが存在する
```

を成功条件にした。

#### 2. Guide Validatorの旧文言依存

Guide PR #100では、Owner 23をV1 Contractへ整理したことで、正しい意味を保ったまま見出し・表現が変わり、旧文字列完全一致Validatorが失敗した。

Rule本文を旧表現へ戻さず、Validatorを次の意味Contractへ更新した。

- Persistence成功を推測しない
- Platform-level lifecycle hookを保証しない
- Workstream / Confirmation / Write Target / Live Guardを分離する
- Wrong Resume後はRoot-Cause-firstで処理する

#### 3. V1導入中InteractionのGuard bootstrap

V1実装開始時点ではLive Guard機構自体がまだ存在しなかったため、実装途中で`recovery-live`を初期化し、そのInteractionのGuardを追加した。

実装後はCanonical Interaction / Conversation Checkpoint / Workstream reference / Indexを1 Git commitで保存してsettlement evidenceを確立し、その後のFinalization Interactionから通常のPre-write Guard Flowへ移行した。

### Current Contract

```text
Current User Message
↓
Indexで候補を絞る
↓
Candidate Checkpointを取得
↓
LLM semantic interpretation
↓
Deterministic hard gates
↓
必要なら1回だけUser Confirmation
↓
Current write target再取得
↓
既存Live Guard settlement確認
↓
Pre-write Live Guard
↓
Repository mutation
↓
Tests / Validation
↓
Canonical Interaction persistence
↓
Live Guard settled
```

Historical / Correction Interactionは履歴Evidenceとして残せるがCurrent Stateを動かさない。Current GitHub evidenceとUserの最新指示は保存済みRecovery stateより優先する。

### Remaining / Platform Boundary

- 通常ChatGPT ConversationにRepository側から強制できるplatform-wide pre-write / post-response / new-Conversation hookが存在すると仮定しない
- 利用可能なProject / Agent / ClientではこのV1 Contractを実行する
- Live Guard呼出し自体が完全にskipされたケースをRepository側だけで100%検出することはできない
- 同一Workstreamへ複数Conversationが完全同時にPre-writeする競合は、必要に応じて既存Lease / atomic coordination Ruleで収束させる
- Capabilityがない環境では「自動保存済み」「自動復帰済み」と偽らずCurrent RepositoryからRecoveryする
