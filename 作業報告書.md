### Requirements / Queue Integrity

Queue内のTask同士が同じRequirements revisionを参照しているだけではCurrent性の証明にならないため、Phase AではQueueが指すRequirementsをTarget Repositoryへ再照合する。

現在の`revisionType: blobSha`では:

```text
Queue control.requirements
+
Target Repository HEAD:<requirements-path>
↓
expected blob SHA == observed blob SHA ?
```

を確認する。

さらにRequirements Fileにuncommitted changeがある場合もCurrent Queue前提が不確実なためfail closedする。

主なblocker:

- repository identity unknown / mismatch
- required source missing / unsafe path
- Queue repository mismatch
- Requirements path unsafe / missing
- revision unsupported / unverified
- Queue revisionとCurrent Commitのmismatch
- Requirements working tree dirty
- Queue not synced
- existing active Run
- Sequential modeで既存active Taskあり
- assignable laneなし

古いQueueをCurrentとしてsilent利用しない。

### Read-only Boundary

Phase A Outputは`authority: derived-loop-dry-run-only`で、Queue / Project StateのAuthorityではない。

`assignmentAuthority`も常に`false`とする。

Policyが将来Phase向けにwrite権限を持っていても、Phase Aの`effectiveForPhaseA`では次を強制的に無効化する。

- working branch write
- commit
- push
- default branch write
- merge
- deploy
- external network
- secret access

Phase AはQueue assignment / Claim / branch / worktree / File mutation / Loop state persistenceも行わない。
