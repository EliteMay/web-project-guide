人が見るためのルール案内

作りたい機能から、必要なルールを探す。

難しい章番号を覚える必要はありません。「保存を付けたい」「検索を作りたい」「サイトが重い」など、やりたいことから確認できます。詳しい条件が必要なときだけ原文へ進んでください。

何をしたい？

まず作業の種類で入口を決めます。全部のルールを読む必要はありません。

機能から探す

機能名か困っていることを検索すると、関係ない項目は自動で隠れます。

保存・データ

Data

ユーザーのデータを残す機能。既存データがある場合は壊さないことが最優先です。

  • 何を、どれくらい、いつ保存するか決める
  • 既存形式を変えるなら移行・Backup・Rollbackを考える
  • Import / Restore後の失敗ケースも確認する

検索・絞り込み・一覧

Findability

「探す対象を知っている人」と「何があるか見たい人」の両方を考えます。

  • 検索だけを壊れた分類の逃げ道にしない
  • Category / Filter / Sort / Recentを必要に応じて組み合わせる
  • 0件時に次の行動を出す

ログイン・認証・権限

Security

誰が何をできるかを先に決め、秘密情報を公開コードへ置かないようにします。

  • 必要な権限だけを渡す
  • 秘密鍵・Token・PasswordをGitHub Pagesへ置かない
  • 拒否・期限切れ・未ログイン状態も作る

Integration

  • 自分側と外部側の責任範囲を分ける
  • Timeout / Retry / 重複Webhookを考える
  • SDKやAPIのVersion・廃止も確認する

Learning

  • Starting KnowledgeとLearning Objectiveを分ける
  • 説明だけでなく必要なPractice / Feedbackを設計する

Web公開・Runtime・Environment

Deploy

Static hostingで十分か、Server実行やSecret-backed処理が必要かをPrimary Taskから判断します。

  • 必要Runtime capabilityからHosting形態を選ぶ
  • Local / Preview / Staging / Productionを目的なく増やさない
  • Pipeline成功だけで本番動作確認済みにしない

Browser

  • Target User / RuntimeからSupport Contractを決める
  • 差が出るBrowser / DeviceをRepresentativeに確認する
  • fallback / polyfillを使う場合はUnsupported pathも確認する

作成・編集・削除

Editing

成功時だけでなく、取消・戻る・Undo・復元まで含めて編集体験を作ります。

  • 頻繁で戻せる操作はUndo / Restoreを優先検討
  • 戻せない重大操作は確認やBackupを入れる
  • 編集中・未保存・保存中・失敗を区別する

画面構成・ナビゲーション・導線

Structure

Sidebarやページ数を先に決めず、ユーザーが何をしたいかから構造を作ります。

  • Goal → Task → 必要情報 / 機能の順で考える
  • 現在地と次に行ける場所を分かるようにする
  • Back / Cancel / Retry / ResumeもFlowに含める

UI・見た目・スマホ対応

UI

装飾より、情報の関係・読みやすさ・操作の見つけやすさを先に整えます。

  • 構造 → Layout → 文字 → 余白 → 色 → Effectの順
  • 全部をCard化・巨大Hero化しない
  • Loading / Empty / Error / Successも確認する

重い・遅い・止まる

Performance

速さだけでなく、遅い端末・大きなデータ・通信失敗時でも主要操作を続けられるようにします。

  • 主要Taskがいつ操作可能になるかを見る
  • Loading / Retry / Timeout / Cancelを考える
  • 長時間利用や大量Dataでも確認する
05 Performance / Reliability

セキュリティ

Security

「個人サイトだから大丈夫」とせず、公開場所・入力・権限・秘密情報を確認します。

  • 公開Repository / Pagesに秘密情報を置かない
  • 外部入力を信用しすぎない
  • 権限は必要最小限にする
06 Security

テスト・完成確認

Quality

「コードを書いた」「Commitした」だけでは完成ではありません。

  • 主要操作が実際に通るか確認する
  • 変更した場所だけでなく影響範囲を見る
  • 実機が必要な項目は未確認を明記する
07 Testing / QualityQuality Checklist

GitHub Pages

Deploy

公開設定だけでなく、実際のURLで表示・リンク・Assetまで確認します。

  • Base pathや404を確認する
  • 公開URLを推測で完成扱いしない
  • 秘密情報を静的配信へ含めない
08 GitHub Pages

Electron・Windows配布

Desktop

InstallerやAuto UpdateはCI成功だけではなく、Windows実機での確認が必要になる場合があります。

  • Setup.exe / Update / 権限を確認する
  • OS固有挙動をCIだけで確認済みにしない
  • 配布後の更新・Rollbackも考える

ライブラリ・CDN・素材

Dependencies

外部依存を増やす前に、本当に必要か・更新や停止時にどうなるかを確認します。

  • Versionと互換性を把握する
  • Assetの出典・Licenseを確認する
  • 外部CDN停止時の影響を見る

エラー調査・診断情報

Diagnostics

「動かない」だけで終わらず、再現条件・状態・原因を追える情報を残します。

  • 必要なログだけを残す
  • 個人情報や秘密情報をログへ出さない
  • 再発時に追えるProject Learningへ繋げる

迷ったときの基本

細かいRuleを読む前に、Guide全体で共通している考え方です。

今のRepositoryを優先する

古い会話・ZIP・記憶より、現在のコード・Requirements・正式仕様を基準にします。

全部のRuleを毎回読まない

作業内容とRiskに関係するOwnerだけを読みます。小さなBugに大規模調査は不要です。

機能より先に目的を見る

「検索画面を作る」ではなく「何を早く見つけたいか」から必要な機能を決めます。

壊す変更は戻せるようにする

Save、Schema、公開、削除などはMigration・Backup・Undo・Rollbackを必要に応じて用意します。

未確認を完成扱いしない

実機や本番で確認していないことは、そのまま未確認として残します。

人に聞く前に調べて決める

RepositoryやEvidenceから合理的に決められることは、細かい承認待ちにせず安全な判断で進めます。
