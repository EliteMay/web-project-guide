0. 共通・基本

  • 最新GitHubをSource of Truthにする
  • 古い会話・ZIP・Memoryを基準にしない
  • 必要なRuleだけ読む
  • 同じRuleの正本を複数作らない
  • Project固有仕様はProject側へ置く
  • 現在のUser指示を優先する
  • 既存仕様を勝手に壊さない
  • 未確認・未実装を完成扱いしない
  • 合理的に決められることはAgent側で決める
  • Meaningfulな作業はPreflightと最終Validationを行う
00 Governance →

1. 要件定義

  • 目的・対象User・Main Taskを決める
  • 必要機能・非対象・保存・崩せない仕様を決める
  • 完成条件を決める
  • 今やる / 後でやる / やらないを分ける
  • 実装済み履歴をRequirementsへ積まない
  • 要件変更時は関連文書も合わせる
01 Requirements →

2. Architecture

  • 責務を明確に分ける
  • 同じ処理を複数箇所へ増やさない
  • 後付けPatchを増殖させず正式経路へ統合する
  • Provider名より必要Capabilityから技術を選ぶ
  • 外部APIとの責任境界を明確にする
  • Smallest Useful Systemから始める
02 Architecture →

3. Data / Storage

  • 大量DataはHTML直書きを避けJSON等へ分離する
  • SchemaとSave形式を明確にする
  • 既存Saveを壊さない
  • Schema変更はMigration / Backup / Restore / Rollbackを考える
  • Import・Sync・Storage failureを想定する
  • 保存成功を確認する
03 Data / Storage →

4. UI / UX / Accessibility

  • User GoalとTask達成を優先する
  • 情報の優先順位と操作を分かりやすくする
  • Loading / Empty / Error / Disabled状態を作る
  • Keyboard / Focus / Contrast / 文字サイズを確認する
  • Mobile / overflowを確認する
  • User-facing UIを未調整のまま完成にしない
04 UI / UX →

5. Visual / デザイン

  • AIテンプレ感を避ける
  • 巨大Hero・過剰Gradient・Glass・角丸Card・CTAを乱用しない
  • Typography・余白・情報密度・Visual hierarchyを整える
  • MeaningfulなVisual変更はResearchしてから決める
  • 別サイトの成功Designをそのまま流用しない
  • 改善しない場合はFoundationから見直す
  • 実装後はBrowser / Screenshotで確認する
18 Visual Research →

6. Structure / Navigation / Flow

  • PageやSidebarから先に決めない
  • Goal → Task → Information / Function → IA → Navigation / Flow → State → Pageの順で考える
  • Back / Cancel / Retry / ResumeもFlowに含める
  • Project固有FlowはProject側へ保存する
  • Visual設計とStructure設計を分ける
22 Structure / Flow →

7. Performance / Reliability

  • Main Taskが早く使えるようにする
  • 不要な処理・一括描画を減らす
  • Retry / Timeout / Cancel / Offlineを考える
  • Slow device・Long session・大量Dataを確認する
  • Third-party failureを全体へ波及させない
  • 数値だけで最適化しすぎない
05 Performance / Reliability →

8. Security

  • SecretをGitHubやFrontendへ置かない
  • 最小権限にする
  • Input / External dataを信用しない
  • Auth境界・Webhook署名を確認する
  • SecretをLogへ出さない
  • Dependency由来Riskも確認する
06 Security →

9. Testing / Quality

  • コードを書いただけで完成にしない
  • Main Flow / Error Flow / Boundary / Regressionを確認する
  • 保存変更はSave / Reload / Restore等を確認する
  • Browser・必要なら実機で確認する
  • Static TestだけでPlaytestを代用しない
  • Cleanup後のFinal Stateを確認する
  • 重大Known Issueが残るなら完成にしない
07 Testing / Quality →

10. GitHub Pages / 公開

  • Publishing Sourceと公開Branchを確認する
  • SPA direct-open / Base path / HTTPS / Domainを確認する
  • Cache / Service Worker問題を考える
  • 公開URLを推測しない
  • 実際に確認できたURLだけ案内する
08 GitHub Pages →

11. Version / Maintenance

  • Versionの正本を1つにする
  • ReleasedとUnreleasedを分ける
  • App / Build / Schema Versionを混同しない
  • Compatibility / Upgrade / Rollbackを考える
  • 古いRuntimeやVersion付きCopyを増やし続けない
  • Release変更はUnreleased historyも同時更新する
09 Version / Maintenance →

12. Project Management / GitHub変更

  • 変更前にCurrent Repositoryを確認する
  • Smallest Safe Changeを優先する
  • 複数File・高Risk変更はBranch / PRを優先する
  • Merge前に最新mainとの差とCIを確認する
  • Merge後mainもValidationする
  • 問題発生時は原因 → Guardが効かなかった理由 → 修正 → 再発防止の順で進める
  • 完了報告では終わったこと・残件・次Actionを明示する
10 Project Management →

13. Electron

  • Webで十分か先に判断する
  • Renderer / Node / IPC境界を安全にする
  • Installer / Auto Update / Rollbackを確認する
  • Windows固有機能は必要に応じて実機確認する
  • CI成功だけで実機確認済みにしない
11 Electron / Distribution →

14. Project Profiles

  • STATIC / DATA / LEARNING / GAME / MEDIA / AI-HANDOFF / CLOUD / ELECTRON / TOOL / PUBLIC-CONTENT を必要に応じて使う
  • ProfileだけでRuleを決めず、変更内容・Runtime・Riskも見る
12 Project Profiles →

15. Dependencies / Assets

  • Dependencyを必要以上に増やさない
  • Version / Compatibility / Deprecationを確認する
  • License・Asset利用条件を確認する
  • CDN停止やSupply-chain Riskを考える
  • GitHub Actions等は可能なら固定参照を使う
13 Dependencies / Assets →

16. Continuous Improvement

  • 同じ失敗を繰り返さない
  • Failure / Success / Anti-patternを記録する
  • Root Causeを一般化し必要ならCommon Ruleへ昇格する
  • 新Rule追加前に既存Ownerへ統合できないか確認する
  • Ruleを増やすだけでなく重複・不要Ruleも整理する
  • 点数だけでAuditを終わらせない
14 Continuous Improvement →

17. Observability / Diagnostics

  • Error原因を追える情報を残す
  • 必要なLogだけ残しSecretを出さない
  • Runtime状態やRemote failureを調査できるようにする
  • Diagnosticsを構造化する
  • Debug処理を本番へ無秩序に残さない
15 Observability →

18. Cross-Repository GitHub

  • 共通GitHub設定は共通Repositoryへ置く
  • Project固有設定を共通化しすぎない
  • Reusable Workflow等は使える範囲で再利用する
  • Repository間の責務を明確にする
  • Guideの判断基準とGitHub実装を分離する
16 Cross-Repository GitHub →

19. Game Development

  • Core Loop / Goal / Progression / Challenge / Rewardを明確にする
  • Failure / Recovery / Save / Tutorial / Feedbackを考える
  • 数値やContent量だけで面白さを判断しない
  • Main Flow変更はActual Playtestする
  • HUD等のMeaningful UIはVisual Researchする
19 Game Development →

20. Learning Site

  • Starting KnowledgeとLearning Objectiveを決める
  • 前提Conceptを説明する
  • 説明だけでなくPracticeを入れる
  • 理解・応用を確認する
  • FeedbackとNext Stepを出す
  • 教材が存在するだけで完成扱いしない
01 Requirements →

21. Research

  • 重要かつ不確実な内容を調査する
  • 一次情報を優先する
  • 複数Sourceと反対Evidenceも見る
  • Source数をGoalにしない
  • Decision Coverage / Saturationで止める
  • Research結果をProject Decisionへ落とす
20 Evidence-first Research →

22. Rule Routing / Preflight

  • Meaningful / Systemic workではPreflightする
  • Work Type / Profile / Risk Signalから必要Ownerを決める
  • 全Guideを毎回読まない
  • Scopeが変わったら再Routingする
  • Human RouterとMachine Routerを合わせる
21 Rule Routing / Preflight →

23. Conversation Persistence / Recovery

  • Guide対象の開発Interactionは可能なら保存する
  • 保存成功を確認し、失敗を保存済み扱いしない
  • Conversation historyをProjectの第二Source of Truthにしない
  • Workstream候補を特定しても自動で作業開始しない
  • 自動推定したResume先は最初にUser確認する
  • 確認後は同じ会話・同じWorkstreamで毎回聞かない
  • Confidence / Confirmation / Write Targetを別Gateにする
  • Userが「違う」と言ったら別候補へ即移動せず、先にRoot Causeと再発防止を処理する
23 Conversation Handoff / Recovery →

24. 会話名

  • Repository名（実装）
  • Repository名（UI・見た目）
  • Repository名（不具合・改善）
  • Repository名（相談・調査）
  • 必要時だけ データ・コンテンツ / GitHub・公開
README →

25. 完成条件

  • Requirements / Specと一致している
  • 保存互換性・Security・Main Flow・Regressionを確認した
  • Browser / UIを確認した
  • 必要なら実機確認、未確認なら明記した
  • CI / 公開状態を確認した
  • Documentation / Learningsを必要に応じて更新した
  • 開発InteractionのPersistenceが必要なら保存成功を確認した
  • 重大Known Issueが残っていない
