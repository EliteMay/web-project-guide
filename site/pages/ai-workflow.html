基本の作業フロー

大きな作業は、だいたいこの順番で狭めていきます。

1

Current Repositoryを確認

README、START_HERE、Requirements、Spec、現在コード、PR / Branchなどから「今どうなっているか」を確定します。

2

作業を分類して必要なOwnerだけ読む

保存ならData、SecurityならSecurity、ゲームならGame、UI構造ならStructure / FlowというようにRouteを絞ります。

3

要件と壊せないものを確認

目的、利用者、主要Task、保存データ、互換性、公開方法などを確認し、既存仕様を勝手に消しません。

4

Research Gate

重要で不確実な判断なら調査へ。原因と正解が明確な小規模修正ならDeep Researchを挟まず進みます。

5

構造 → 実装

大きなUIではGoal → Task → Information / Function → IA → Navigation / Flow → State → Pageの順に考え、見た目だけ先に固定しません。

6

Validation

実装したファイルだけではなく、最終Commit / 本番 / Browser / 実機など、必要な最終状態で確認します。

最近追加・強化された専門Route

同じ「Web制作」でも、学習、Runtime、Browser、外部連携では確認する事実と失敗条件が違います。

学習・解説

教材があるだけで完成にせず、開始知識、学習目標、前提、説明 / Practice、理解・応用Evidence、Feedback、Next Stepを確認します。

Web Deployment / Runtime

Provider名を先に決めず、Static files、Server execution、Secret、Background workなど必要Capabilityから形を選びます。

Browser互換性

Compatibility表だけで完成扱いせず、Target User / Runtimeに合うRepresentative Browser / DeviceでPrimary Taskを確認します。

外部Integration

HTTP成功だけをOracleにせず、Auth、Authority、Retry、Duplicate、Provider failure、Version lifecycleまでProduct behaviorとして確認します。

Research Gate：いつ論文を見る？

「何でも論文を探す」ではなく、重要度と不確実性で調査の深さを変えます。

Quick Research

Version、仕様、対応有無、日付などの単純な事実。公式資料や一次Sourceで確認できれば終わります。

Standard Research

普通の比較や改善判断。複数の独立Source、Alternative、Limit、Projectへの適用可能性を確認します。

Deep Research

重要かつ不確実な判断。既存研究、Original Source、賛成・反対Evidence、Bias、Failure、Evidence Mapまで確認します。

Academic EvidenceがあるTopic

Systematic Review → Meta-analysis → Peer-reviewed Paper → Independent Replication → Experimentなどを優先候補にします。

Software / Platform仕様

公式Documentation、Standards、一次Sourceを優先します。古いBlogだけで現在仕様を決めません。

UI / Productの使われ方

Real Product、User Research、Case Study、実際のSite / Game、必要ならCommunityの実利用Evidenceも見ます。

検索しても決まらない

無限に調査を続けず、Prototype、Measurement、Playtest、User TestなどProject内の検証へ移します。

AIが勝手に進める範囲 / 止まる範囲

何でも確認待ちにするのでも、何でも勝手に決めるのでもありません。

状況AIの動き
Current Repoと既存Intentから合理的に決められるBest Reasonable Decisionで進める。細かい確認を毎回返さない。
既存仕様を壊さず安全に直せる小変更必要Ownerだけ確認し、Smallest Safe Changeで修正してValidation。
重大な仕様変更・削除・Normative Owner衝突勝手に決めず、その変更経路を止めてUser Decisionへ。
Source / Branch / PR / Runが一意に復旧できない推測で上書きせず、Recovery / unresolvedとして止める。
Validationが失敗した完成扱いしない。原因を直すか、未確認として明示する。
